# Changelog

## [Unreleased]

### Added
- Certificate pinning for HTTPS LAN backends. Until now every `backend_https` route was proxied with `secure: false` — no chain check, no hostname check — because LAN targets (DSM on `:5001`, Proxmox on `:8006`, router admin UIs) are practically always self-signed. That protects the bytes but not the identity: anything that manages to answer on `host:port` was accepted. A route may now carry `backend_tls_fingerprint`, the SHA-256 of the backend's leaf certificate (64 lowercase hex chars), and the gateway then verifies the certificate the backend actually presents against it. New `src/proxy/tlsPin.js` supplies a per-request `https.Agent` (cached per host/port/fingerprint) whose `createConnection` hands the connected socket to the HTTP client **only after** the fingerprint matched — Node's `http.Agent` parks the request until the callback fires, so on a mismatch not one byte of the request (request line, headers, `Authorization`, body) is written to the backend. The socket is destroyed immediately; pinned agents run with `keepAlive: false` so a rejected peer can never be pooled and reused, and with `maxCachedSessions: 0` because a resumed TLS session skips certificate presentation and would leave nothing to pin against. Covers the WebSocket-upgrade path too (http-proxy honours a per-request `agent` on `proxy.ws` exactly as on `proxy.web`) — a pinned Proxmox noVNC console is verified the same way as a plain request. A route **without** a fingerprint keeps today's behaviour byte-for-byte: `secure: false`, no verification, no new failure mode.
- Pinning failures fail closed and are loud. A mismatch answers the web path with **502** and the existing plain-text upstream-error body (`Gateway upstream error: ERR_TLS_PIN_MISMATCH`), destroys the socket on the upgrade path, and logs at `error` with route domain, route id, `host:port`, and the expected vs. seen fingerprint (certificate fingerprints are public metadata, not secrets — printing both is what makes "backend cert was renewed" distinguishable from "something else is answering on that address"). WoL is *not* triggered for a pin mismatch, only for `ECONNREFUSED` as before. A fingerprint that is present but unusable (not 64 hex chars after normalisation) is treated as a broken route, not as "no pinning": the HTTPS route is refused with 502 `ERR_TLS_PIN_CONFIG` and logged, so a typo can never silently downgrade a pinned route to an unverified one. A fingerprint on a **plain-http** route is the one case that only warns — there is no TLS to verify there, so refusing would take a working route down without protecting anything (it can only arise from a stale fingerprint left behind when a route was switched back to `http://`). The colon-separated, uppercase and `sha256:`-prefixed spellings of a fingerprint are accepted — they denote the same certificate and each of OpenSSL, browsers and Node prints a different one.

- Heartbeat now reports `lan_ip` — this gateway's own primary RFC1918 LAN IPv4. The server uses it to rewrite a co-located service's loopback target (`127.0.0.1`) to the host's real LAN address when that route has failed over to a sibling gateway (HTTP `X-Gateway-Target` and L4/SSH/RDP config push). The address is picked from physical-LAN interfaces only (WireGuard/docker/VPN excluded), preferring the subnet that contains the host default route; public/loopback/link-local addresses are never reported. A host with no private LAN address reports `null`, and the server then degrades safely (HTTP 502 / no L4 listener) instead of mis-forwarding. Companion side of the server's gateway-loopback-failover feature.

### Fixed
- Security: cleared the high-severity `tmp` advisory (GHSA-52f5-9888-hmc6 / GHSA-ph9p-34f9-6g65 — symlink/path-traversal arbitrary write) by pinning `tmp ≥ 0.2.7` via `overrides`. `tmp` is reached only transitively through the dev-only `@stryker-mutator/core → @inquirer/prompts → external-editor` chain (mutation testing) and is never shipped in the production image (`npm ci --omit=dev`); the override avoids the breaking Stryker 9 major bump that `npm audit fix --force` proposed. Also pinned production `qs ≥ 6.15.2` (GHSA-q8mj-m7cp-5q26 — `qs.stringify` DoS, reached via `express`/`body-parser`). Lockfile + `overrides`-only change; no source change, all tests green. The 2 remaining `ajv` advisories are moderate, dev-only (Stryker), and below the CI `--audit-level=high` gate — left untouched to avoid forcing ESLint's `ajv@6` to a breaking major.
- A failed TCP listener bind no longer crashes the gateway. `TcpProxyManager.setRoutes` applied L4 routes in one sequential `await` loop, so the first `EADDRINUSE` (a host process already owns the port under `network_mode: host`, or two routes share a `listen_port`) rejected the whole method — and since `setRoutes` runs inside an `async` EventEmitter `'change'` listener in `bootstrap.js`, that rejection was unhandled. On Node's default `unhandledRejection` mode (`throw`) it terminated the process, and because a persistently-conflicting config is re-applied on every poll (and on the initial bootstrap poll), the result was a **crash-loop** on a remote, hard-to-reach gateway. Each route is now applied in isolation: a bind failure is logged (`routeId`, `listenPort`, `EADDRINUSE`) and skipped, sibling routes are unaffected, and `setRoutes` resolves. A process-level `unhandledRejection` handler in `src/index.js` is added as a final safety net so any future async-listener rejection logs loudly and keeps the gateway alive instead of crash-looping.
- WebSocket upgrades are now proxied through the gateway. `src/proxy/http.js` only ever called `proxy.web()` from the `request` handler and never registered an `'upgrade'` handler, so Node silently dropped WebSocket upgrades — breaking any backend that relies on them behind a gateway route, most visibly the **Proxmox noVNC/xterm.js console** (which tunnels VNC over a WebSocket on the same `:8006` backend port, *not* on a separate VNC port). Plain HTTP worked, the console hung. The proxy now forwards upgrades via `proxy.ws()`, reusing the same `X-Gateway-Target-Domain` routing and the per-route `backend_https` flag to pick `ws://` vs `wss://`. `X-Gateway-*` headers are stripped on the ws path too (`proxyReqWs`), and the shared `error` handler now distinguishes `ServerResponse` (web) from `Socket` (ws) so a failed upstream upgrade can't crash the gateway. No server-side, Caddy or route-config change is required — WebSocket support is transparent for every gateway route.
- Security: bumped `axios` 1.15.0 → 1.16.1 and pinned `fast-uri` ≥ 3.1.2 (via `overrides`) to clear all high-severity `npm audit` advisories — prototype-pollution / NO_PROXY-bypass gadgets in axios and path-traversal in fast-uri. `fast-uri` is reached only transitively through the dev-only Stryker→ajv chain and is never shipped in the production image (`npm ci --omit=dev`); axios is the production HTTP client for heartbeat + config sync. Lockfile-only change to dependencies, no source change.
- Heartbeat and config-sync now use dedicated HTTP/HTTPS agents with `keepAlive: false`. Node 20's global agent defaults to keep-alive, which caused stale TLS sockets to be reused after network hiccups — server responded with `TLS alert 80 (internal_error)` on every subsequent request until the container was restarted.
- Lint: switched to `plugin:security/recommended-legacy` for compatibility with ESLint 8 (`eslint-plugin-security@3` dropped legacy-config support from `recommended`).
- `wireguard.runCommand` accepts a `timeoutMs` option and `getStatus()` now uses `1500ms` so a wedged `wg show` (rare but observed after TUN-device hiccups) can no longer block the self-check or heartbeat collection indefinitely. `wg-quick up/down` continues to run unbounded since boot-time setup can legitimately take longer.
- `startHeartbeatTicker` caps `getHealth()` at 8s (`Promise.race`). When the cap fires the gateway still sends a heartbeat with `{ overall_healthy: false, reason: 'health_collection_timeout' }` so the server's state machine sees liveness and the operator sees the timeout reason in `last_health` for diagnosis. Default cap is below the heartbeat HTTP-timeout (10s) so the next tick can land before the previous overruns it.

### Changed
- `@callmetechie/gatecontrol-config-hash` pinned to `^1.3.0`, the version that carries `backend_tls_fingerprint` in `GatewayConfigSchema`. The schema `.strip()`s unknown keys, so with 1.2.0 the field is dropped from the canonical form the gateway hashes while the server (on 1.3.0) hashes it — every pinned route would report a `Hash mismatch` on each poll. `CONFIG_HASH_VERSION` stays at **2**: the new field is `.nullish()` with no `.default()`, so a route without a fingerprint canonicalizes exactly as before and no existing config hash moves. Same rationale as the `^1.2.0` pin for `egress_routes`.
- `X-Gateway-*` request headers are now stripped from the *incoming* request in `targetFor()`, right after the target domain has been read, instead of only from the outgoing request in the `proxyReq` hook. http-proxy fires `proxyReq` from the outgoing request's `socket` event, and a pinned route does not get a socket until the TLS handshake has completed — by then the outgoing header block is already rendered and `removeHeader()` throws `ERR_HTTP_HEADERS_SENT`. Stripping at the source keeps the headers off the wire on every path; the `proxyReq`/`proxyReqWs` hooks remain as a safety net and now no-op once headers are rendered.
- Self-check wiring centralised in `src/health/selfCheckRunner.js`. Both `/api/status` and the heartbeat ticker now call a single `runHealthCheck()` closure built once at bootstrap time — previously the route-list, DNS resolver and reachability probe were duplicated across two call-sites in `bootstrap.js`. L4 routes get a synthesized `domain: 'l4:<port>'` label in `route_reachability` (was undefined for the heartbeat path before).
- Mutation-test coverage extended for `wol._computeBroadcast` (octet-range boundaries, /16, /32), `wol.validateMac` (length / hex), `config.isRfc1918` (exact 10/8, 172.16/12, 169.254/16 and 192.168/16 boundaries) and `proxy/router` (`wol_enabled` ternary). Aim is to retire the `break = 45` floor in stryker.conf.json on the next mutation run.
- Mutation `break` threshold lowered to 45 to reflect actual current score (49.58). `high`/`low` remain at 90/80 as aspirational targets — surviving mutants in `wol.js`, `config.js`, `router.js` need follow-up test coverage.
- Docker HEALTHCHECK now runs a dedicated `src/healthcheck.js` that parses `/config/gateway.env` directly. The previous inline `node -e` probe relied on `process.env.GC_TUNNEL_IP` / `GC_API_PORT`, but those variables live in the volume-mounted env file and are never exposed to the container's Docker ENV — the Node runtime reads the file and keeps the values in-memory, so a separate probe process sees nothing. Start-period raised to 60s to accommodate WG bring-up.
- `/api/health` is now registered before the `/api` auth-middleware mount. Previously the auth guard matched first and rejected every unauthenticated probe with 401, so the health endpoint was unreachable despite its comment claiming otherwise.

## [1.0.0] — 2026-04-18

### Added
- Initial release
- HTTP reverse proxy with X-Gateway-Target header routing
- TCP port forwarder with dual-bind overlap for port changes
- Wake-on-LAN via SO_BROADCAST (no NET_RAW)
- Hybrid pull + push config sync with @callmetechie/gatecontrol-config-hash
- 4-layer self-check (process + network + per-route + end-to-end)
- Heartbeat ticker to server with health payload
- Multi-arch Docker image (amd64, arm64, arm/v7)
- Security-hardened container: non-root user, cap_drop ALL, read-only FS
- Platform deployment guides (Linux, Synology DSM 7.2+, Pi, migration from dwg)
